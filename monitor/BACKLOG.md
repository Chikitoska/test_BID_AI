## P0 — простыми словами (для начинающих)

Два самых важных «подводных камня». Если их не починить, можно либо **ложную тревогу** получить, либо **реальный простой ЛК пропустить**.

### Словарь (без боли)

| Слово | Что это |
|--------|---------|
| **health** | Лёгкая проверка каждые ~5 мин: лендинг открывается + минимальный вход в ЛК (логин, ФИО, компания). «Пульс» PROD. |
| **TG** | Telegram — куда приходят алерты («сайт/ЛК лежит»). |
| **WebDriver / Chrome** | Автоматический браузер на сервере. Через него health и боевые тесты «заходят» в ЛК как человек. |
| **antiflap** (антифлап) | Защита от спама: не орать в TG на *каждый* одиночный сбой. Ждём подтверждения (повтор / несколько FAIL подряд). |
| **флак** | Разовый сбой «само прошло»: тормоза, краш браузера, таймаут — сайт при этом может быть жив. |

### 1) Chrome-флаки vs «ЛК реально лежит»

**Аналогия:** сигнализация в доме.

- Соседский кот задел датчик → сирена. Это **флак**: сработало «железо/датчик», дом цел.
- В квартиру реально залезли → сирена. Это **настоящий инцидент**.

Сейчас health иногда падает из‑за **Chrome/WebDriver** (браузер на VPS завис, chromedriver умер, пустой `Message:` в стеке) — и в TG это выглядит почти так же, как «ЛК вернул `/error/500`». Мозг читает: «PROD лежит», а на деле **BID мог быть жив**, а споткнулся робот-вахтёр.

**Что не так сейчас**

- В **боевом pytest** ЛК уже есть разделение: UI-флак → только Grafana; сеть/5xx → TG.
- В **health** такого же чёткого «это инфра браузера, не ЛК» часто нет → ложный пейдж.

**Что сделать**

- Отличать класс **`infra`** (Chrome/WebDriver) от **«ЛК лежит»** (логин/страница `/error/4xx|/error/5xx`, сеть BID).
- В TG не слать infra как «ЛК упал»; при желании — отдельный мягкий сигнал или только Grafana + confirm/retry.

**Зачем:** меньше ложных TG при живом BID.  
**Риск правки:** низкий, если путь 4xx/5xx и сетевые ошибки **не ослаблять**.

### 2) Chrome занят → health зелёный, хотя ЛК не проверяли

**Аналогия:** вахтёр ушёл курить.

Каждые 5 минут health хочет зайти в ЛК через Chrome. Но на сервере **один** браузер: если в это время идёт длинный **lk pytest**, Chrome **занят** (файл-замок `chrome_lock`).

Что делает health сейчас:

1. Лендинг по HTTP проверил → ок.
2. В ЛК зайти не смог → пишет `SKIP LK: Chrome занят…`.
3. Итог прогона всё равно **OK** (зелёный).

То есть вахтёр **не обошёл этаж с ЛК**, но в журнале смены стоит **«всё нормально»**. Если ЛК в эти 5–15 минут реально лежал — **в TG тишина**, на графике может быть зелёный столбец без проверки ЛК.

**Что сделать**

- Не считать такой прогон полноценным **OK**.
- Статус вроде **`skipped`** / «ЛК не проверяли» + **метрика в Grafana** (видно «дыру проверки»).
- В TG из‑за busy **не пейджить** (иначе шум при каждом пересечении с pytest) — важна **видимость**, не сирена.

**Зачем:** не маскировать слепую зону по ЛК.  
**Риск правки:** средний — если начать алертить каждый busy, будет спам; правильный баланс — статус/метрика без пейджа.

## Уже хорошо — не ломать

- Health каждые ~5 мин = быстрый пульс PROD (лендинг + мин. ЛК).
- Antiflap / streak: не спамить TG на каждый одиночный FAIL.
- Подтверждённый HTTP 4xx/5xx после in-run retry → алерт сразу.
- В lk pytest: UI-флаки (Timeout/assert/селектор) → Grafana only; сеть/массовый FAIL → TG.

- Telegram с VPS через **GitHub relay** (без прямого `api.telegram.org` с сервера).
- Influx + Grafana + digest-отчёты — контур наблюдения уже живой.
